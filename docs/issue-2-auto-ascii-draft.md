# 代码输入自动切英文：暂存方案

- 关联问题：`andelf/remi-znabc#2`
- 日期：2026 年 11 月 8 日
- 状态：Draft，暂缓实现；仅保存设计与核查结果
- 核查基线：`1c04b5d`，已包含 #1 的连续输入修复

## 目标与交付范围

用户忘记切换英文时，利用代码中的明确特征识别误输入，原样输出尚未提交的编码和本次触发字符，并切到英文，后续由用户主动切回中文。

此功能会改变编码、提交及中西文状态，误判可能把原本想输入的中文直接提交为英文。本次仅创建 Draft PR 暂存方案，不增加运行开关，不修改 processor、schema、词库或用户安装。Issue #2 继续保持开放。

以下规则是供后续评审的候选方案，不代表已批准实现或已通过功能验收。

## 当前实现核查

在全新用户目录安装基线方案，通过 Linux x86_64 的真实 `librime 1.17.0 + librime-lua` 逐键观察，关闭个人学习。大写字母及 `_`、`(` 使用对应的 Shift 修饰位；探针将 Rime 提交文本与未被处理、应交给应用的可打印按键合并为“应用输出”。

| 输入序列 | 应用输出 | 尚未提交的编码 | `ascii_mode` |
| --- | --- | --- | --- |
| `foo_bar` | `foo_` | `bar` | false |
| `fooBar` | `fooB` | `ar` | false |
| `Foo` | `F` | `oo` | false |
| `foo(` | `foo(` | 空 | false |
| `foo=` | `foo=` | 空 | false |
| `_` | `_` | 空 | false |
| `(` | `(` | 空 | false |

部分字符已经使原始编码输出，但不会持续切换为英文，随后的字母仍进入中文编码。该核查是 Rime API 探针结果，未覆盖 macOS / Windows 前端完整物理键盘事件；探针保存在本地忽略目录，尚未成为仓库正式回归测试。

相关入口：

- [schema](../rime/znabc.schema.yaml) 的 `ascii_mode`、`ascii_composer`、speller 字母表和标点配置。
- [processor](../rime/lua/znabc_processor.lua) 的特殊输入、形码、选单确认和标点处理。
- [学习处理](../rime/lua/znabc/learning.lua) 的正常中文提交边界。
- [#1 规格](issue-1-continuous-input-spec.md) 的选单继续输入语义。

## 不能直接采用的宽泛规则

Issue 中的“首键不是小写字母”以及“字母串中出现非数字符号”会命中以下合法中文操作。它们均需单独定义优先级。

| 已有操作 | 冲突 |
| --- | --- |
| `3235` 纯笔形 | 首键为数字，不能自动视作误输入 |
| `I123 → Space` 输出“壹贰叁” | 首键为大写字母，但有既有数量词语义 |
| `xi'an` | 单引号是音节分隔符 |
| `shijie] → Space` | 方括号用于以词定字，GBK 选单中还用于翻页 |
| `nihao,` / `nihao.` | 当前输出“你好，” / “你好。”，标点需保留中文语义 |
| `vLove`、`v1` | 已有临时英文和符号选单，不应被新规则提前改写 |
| 选单中的 `-`、`=` | 已用于翻页 |
| Shift、Caps Lock 与快捷键 | 已由前置 `ascii_composer` 及现有快捷键处理 |

## 候选设计边界

1. **显式开启，默认关闭。** 如果后续实施，增加独立功能开关；关闭时保持现有行为。当前 Draft 不添加该开关。
2. **限定识别阶段。** 只考虑普通中文编码阶段、光标位于串尾且尚未进入选词的输入。已打开选单、有已选分段、GBK 和特殊输入暂不识别。
3. **使用明确触发集合。** 首批可讨论普通串中的大写字母、`_` 和 `(`。不要用“所有非小写字符”或“所有标点”作为判定。首键触发集合与串中触发集合分别评审。
4. **保留现有输入优先级。** 数字形码、单引号、方括号、中文标点和 `i/I/v` 模式优先。代价是这些前缀的代码标识符可能仍无法自动识别，需要用户手动切换。
5. **原样输出一次。** 保存未提交的原码，清理旧 composition，再原样提交原码与触发字符；消费本次事件，避免字符丢失、重复或被后续标点处理转换。不确认中文候选，也不记录中文学习。
6. **持续英文。** 设置 `ascii_mode=true` 后，在当前会话后续输入中维持英文，用户通过既有手动切换操作返回中文。跨应用、跨会话及重启后的状态恢复不在本轮候选范围。
7. **保留控制事件。** 不将释放事件、Ctrl / Alt / Super 快捷键、方向键、功能键和单独 Shift 视为代码内容。带 Shift 的大写字符和符号需按最终可打印字符识别。
8. **不回收已提交文本。** 自动识别只能处理当前未提交输入；不能撤回 #1 或用户此前操作已经提交到应用的内容。

处理位置需要同时考虑前置 `ascii_composer` 和 processor 内的特殊输入分支。仅设置 `ascii_mode` 后返回，不能假定当前事件会重新经过前置处理器；应以真实逐键测试确认一次提交与一次消费。

## 待决定事项

- 功能开关名称、设置入口，以及是否需要应用级启用范围。
- 大写首字母是否触发；`I` 数量词优先级如何展示给用户。
- 除 `_`、`(` 外是否支持 `= / \\ { } @ #` 等字符；其中哪些已有输入语义需要保留。
- `i/v` 开头代码与现有特殊模式的取舍；本草案暂按现有模式优先。
- 全角设置、非美式键盘、死键及前端传入的 keycode / 修饰位差异。
- 自动切换后的状态提示，以及误判后手动恢复的体验。

这些问题明确前，保持 Draft，不进入实现或启用阶段。

## 后续实现的验收清单

以下是未来测试要求，本次未实现这些行为：

| 场景 | 预期 |
| --- | --- |
| 功能关闭 | 现有完整回归通过，输入行为不变 |
| 普通编码 `foo_bar`、`fooBar`、`foo(` | 对已批准的触发字符，输出逐字符一致，最终无中文 composition，进入英文 |
| 自动切英文后继续输入、空格、回车和下一串代码 | 持续英文，不因提交或新词开始自动返回中文 |
| 用户主动切回中文 | 后续中文编码及 #1 连续输入正常 |
| 空输入时的大小写、数字和符号 | 严格遵循最终批准的首键集合，不吞键 |
| `I123`、`vLove`、`v1`、`3235`、`xi'an`、`shijie]` | 各自既有功能正常 |
| `nihao,`、`nihao.` 和选单翻页 | 保持中文标点及选择语义 |
| 选单中已有高亮、人工分段选择 | 按明确排除规则运行，不把已选中文或旧编码重复提交 |
| 光标中间、Ctrl / Alt / Super、释放及功能键 | 不误触发，不影响应用快捷键 |
| 原文输出后检查用户词与使用次数 | 不生成中文用户词，不增加中文候选使用次数 |
| macOS / Windows 前端与不同键盘布局 | 物理按键验证字符完整、无双重提交，模式切换可见且可手动恢复 |

正式实现需把以上要求落为自动回归，并为无法自动覆盖的前端场景记录实际验证范围。此次文档仅记录现状和设计，不把候选方案描述为已实现功能。
